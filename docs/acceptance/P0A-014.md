## Tick contract

- At `t_k = k * control_dt_s`, the authoritative runner observes the
  current simulated rigid-body state through the existing sensor model.
  A streamed mission reference enters on the first tick at or after its
  timestamp, then holds through the next update. Future reference values
  never interpolate backwards into that stream. Stock smooth routes are
  explicitly `planned`: the complete exogenous trajectory and its slopes
  are authored before launch. Changing a planned endpoint changes the
  trajectory issued during its segment. Live updates use the streamed
  contract. No logged drive or auxiliary channels enter autonomous control.
- The controller produces the requested body-axis rotor wrench and the
  nominal mixed rotor thrusts. The existing tick-start SOC bus solve
  resolves each branch at its loaded voltage, determines the supported
  quasi-static RPM/thrust ceiling, and solves current for delivered load.
  RK4 integrates only the applied rotor forces and moments plus the
  modeled body forces. A disturbance is sampled at the same tick
  boundary. It cannot enter across RK substeps of the preceding tick.
- The next tick consumes the prior tick's evolved rigid state and pack
  SOC. The previous delivery residual also feeds the controller's
  integral update. It blocks integration only when the residual exceeds
  the existing allocation tolerance and the new error demands more of
  the unavailable wrench in that axis. It allows unwinding, retains the
  PID's existing limits and does not introduce a new actuator transient.
- `ScenarioResult.times` remains the start of each attempted control tick.
  The clock trace records the start state, requested wrench, nominal
  branch requests, actual applied rotor wrench, previous residual, rigid
  state time, SOC time and whether integration occurred. Wrench order is
  [collective N, body roll N m, pitch N m, yaw N m]. Trajectory state is
  stamped at `t_{k+1}` on an integrated tick. A critical refusal applies no
  wrench and retains the start state. In-tick electrical crossings retain
  the existing partial charge and energy accounting through the crossing.
- The shared offline flight command `scripts/run_simulation.py --scenario flight`
  uses the same `scenarios/service.py` entry point as the API. Its JSON
  exposes the autonomous mode and clocks, branch RPM, voltage and ceilings,
  requested and applied wrenches, and missing terminal electrical samples
  without inventing values. The supervised CAD-only worker and its frozen
  request protocol are outside this flight path.

## Verdict contract

- The P0A-006 cutoff bracket retains equality as a breach. Battery
  cutoff and demonstrated constant-power demand violations emit a
  `battery:pack` finding with pack ID, limit, value, threshold, unit and
  event time, alongside the compatible aggregate battery verdict.
- A failed iterate, out-of-range bus point or exhausted solve by itself
  gives `INCONCLUSIVE`. On an unsupported loaded solve, a separate check
  may establish a **fixed-demand** power violation: evaluate the nominal
  no-derating demand at a supported open-circuit-voltage point and test
  it against the P0A-006 constant-power limit. The check is unavailable
  if OCV/RPM support or a direct bus connection is missing. This is a
  model limit on the fixed request, without a post-collapse prediction.
- P0A-012 per-branch hard limits retain structured `FAIL`. A supported
  cutout remains failed even if the controller continues with the
  remaining actuators. Unmodeled winding drag or other unsupported
  mechanisms stop before issuing a command on the affected tick.
  No terminal branch finding invents recovery. No study-specific
  QDrone threshold enters this plant.
